# Codex Rules

## 1. 总原则

本项目是长期复杂项目，后续 Codex 会话必须保守、小步、可验证地推进。任何一次会话都不应该试图实现整个系统，也不应该无边界读取大型参考项目。

核心规则：

- 每次只做一个小任务。
- 修改前先说明计划。
- 修改后总结改动、运行方式和测试方式。
- 优先读取当前项目文档，再读取相关代码。
- 参考项目必须分批、定向读取。
- 不允许一次性复制参考项目。
- 不允许大规模无边界重构。
- 不允许绕过自主性权限设计去实现自动执行。

## 2. 如何避免上下文爆炸

每次会话开始时：

1. 先阅读 `AGENTS.md`。
2. 根据任务阅读必要文档，例如：
   - 产品问题读 `docs/product/PRODUCT_SPEC.md`。
   - 架构问题读 `docs/architecture/SYSTEM_ARCHITECTURE.md`。
   - 开发阶段问题读 `docs/codex-tasks/DEVELOPMENT_ROADMAP.md`。
   - Codex 工作约束读 `docs/codex-tasks/CODEX_RULES.md`。
3. 只读取和当前任务直接相关的目录。
4. 不要递归读取整个仓库。
5. 不要同时分析多个大型参考项目。

读取文件时应优先：

- 使用 `rg --files` 查找文件。
- 使用 `rg` 搜索关键词。
- 只打开必要文件。
- 对长文件先看目录、标题、导出项或关键函数。

不应：

- 一次性打开大型目录下所有文件。
- 同时读取 Web、Desktop、AI core、DB 和参考项目。
- 为了“全面了解”读取无关文件。

## 3. 如何读取参考项目

参考项目位于 `E:\code` 下：

- `E:\code\harness-main`
- `E:\code\ccx`
- `E:\code\claude-desktop-app-main`

读取规则：

- 只有用户明确要求分析某个参考项目时，才允许读取该项目。
- 一次会话只分析一个参考项目。
- 必须先说明本次分析目标和待读取范围。
- 先看目录结构，再按关键词查找相关模块。
- 输出分析文档到 `docs/reference-analysis`。
- 分析文档应包含可借鉴设计、适配建议和风险。
- 不能把参考项目代码直接复制到当前项目。

推荐分析顺序：

1. `harness-main`：高自主性 Agent、低模型任务执行、重复任务自动化、Skill 生成、工具调用、权限控制、任务状态管理。
2. `ccx`：三层记忆压缩、记忆检索、后台工具调用、Agent 运行机制。
3. `claude-desktop-app-main`：前端结构、对话 UI、设置页面、桌面端交互方式。

禁止：

- 在一个会话里同时读取三个参考项目。
- 使用脚本批量复制参考项目。
- 将参考项目结构不加判断地搬进当前项目。
- 在没有分析文档的情况下直接实现大模块。

## 4. 每次只能做一个小任务

好的任务示例：

- “只初始化 monorepo 配置，不写业务代码。”
- “只设计 Prisma schema 初稿。”
- “只实现 Markdown 章节解析。”
- “只实现自主性权限判断函数和测试。”
- “只实现 Skill manifest 校验。”

不好的任务示例：

- “把整个系统做完。”
- “参考三个项目实现完整 Agent。”
- “一次性做 Web、Desktop、Skill 社区和推荐算法。”
- “重构所有 packages。”

如果用户任务过大，Codex 应先拆分阶段，并建议从最小可验证任务开始。

## 5. 修改前计划规则

每次修改前，Codex 必须用简短计划说明：

- 将修改哪些文件或目录。
- 不会修改哪些范围。
- 本次验收标准是什么。
- 是否需要读取参考项目。

计划示例：

```text
本次只修改 packages/ai-core/src/autonomy，新增权限判断类型和纯函数测试。
不接入 Desktop，不实现真实工具调用，不读取参考项目。
验收标准是测试覆盖只回答、只读、写入和高风险确认四种情况。
```

## 6. 完成后总结规则

每次完成后必须总结：

- 修改了哪些文件。
- 每个文件的用途。
- 如何运行。
- 如何测试。
- 没有完成或故意不做的内容。
- 后续建议任务。

如果没有测试命令或测试尚未配置，需要明确说明。

## 7. 业务代码规则

在被要求写业务代码前，不要写业务代码。

写业务代码时：

- 优先遵守现有目录结构。
- 先实现最小闭环。
- 先写类型和边界，再写复杂实现。
- 对 AI、权限、工具调用、Skill 执行这类高风险能力必须有日志和测试。
- 不要把 LLM 调用散落在 UI 组件中。
- 不要把权限判断写死在按钮或页面里。
- 不要让社区 Skill 默认自动执行。

## 8. 架构变更规则

允许：

- 小范围补充文档。
- 为当前任务新增必要类型。
- 为当前任务新增局部模块。
- 根据已完成参考分析修订架构。

不允许：

- 无边界重命名目录。
- 一次性调整所有包结构。
- 删除用户已有文件。
- 改动与当前任务无关的模块。
- 以“顺手”为理由做大规模重构。

## 9. AI 和安全规则

涉及 AI Agent、工具调用、Skill 和自主性时，必须遵守：

- 所有工具调用必须能被记录。
- 所有写入操作必须有风险等级。
- 高风险操作必须确认。
- 社区 Skill 默认不可自动执行。
- Skill 安装前必须展示风险等级、所需工具、所需自主性等级和安全说明。
- 自动生成 Skill 必须先生成草案，不可直接启用。
- 记忆压缩必须保留来源和更新时间。
- 检索结果必须保留来源，避免无法审计。

## 10. 文档维护规则

当实现改变架构或产品范围时，应同步更新相关文档：

- 产品范围变化：更新 `docs/product/PRODUCT_SPEC.md`。
- 架构或数据流变化：更新 `docs/architecture/SYSTEM_ARCHITECTURE.md`。
- 开发阶段变化：更新 `docs/codex-tasks/DEVELOPMENT_ROADMAP.md`。
- Codex 工作方式变化：更新 `docs/codex-tasks/CODEX_RULES.md` 和 `AGENTS.md`。

文档更新也应小步进行，不要一次性重写所有文档。

## 11. 测试与验证规则

后续开发中：

- 纯函数逻辑应优先有单元测试。
- 权限判断、Skill manifest、书籍切分、评分算法必须有测试。
- Web 关键流程后续应有 Playwright 测试。
- Desktop 工具调用和任务日志应有可验证状态。
- 没有测试时，必须说明未测试原因。

测试命令尚未正式确定前，可以在 `AGENTS.md` 中保留占位。

## 12. 当前阶段特别约束

- 只创建文档。
- 不写业务代码。
- 不读取 `E:\code` 下三个参考项目。
- 不初始化框架。
- 不安装依赖。
- 不修改 `schema.prisma` 内容。
