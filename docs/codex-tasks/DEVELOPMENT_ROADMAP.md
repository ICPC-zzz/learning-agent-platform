# Development Roadmap

## 1. 路线图原则

这是一个长期复杂项目，必须分阶段、小步、可验证地开发。每次 Codex 会话只处理一个明确任务，不能同时实现网站、Agent、Skill 社区和学习算法。

每个阶段都应包含：

- 本阶段目标。
- 推荐任务。
- 验收标准。
- 明确不做什么。
- 后续对话建议。

## 2. Phase 0：项目总控与约束

目标：

- 创建项目总控文档。
- 明确产品范围、架构边界、开发路线和 Codex 工作规则。
- 避免后续会话上下文爆炸。

验收标准：

- `PRODUCT_SPEC.md` 存在并描述产品愿景和 MVP 范围。
- `SYSTEM_ARCHITECTURE.md` 存在并描述模块职责和核心流程。
- `DEVELOPMENT_ROADMAP.md` 存在并拆分阶段任务。
- `CODEX_RULES.md` 存在并约束后续 Codex 工作方式。
- `AGENTS.md` 存在并作为仓库入口规则。

本阶段不做：

- 不写业务代码。
- 不读取参考项目。
- 不初始化框架。
- 不设计完整数据库 schema。

推荐后续 Codex 对话：

1. 分析 `E:\code\harness-main`，只产出参考分析文档。
2. 分析 `E:\code\ccx`，只产出参考分析文档。
3. 分析 `E:\code\claude-desktop-app-main`，只产出参考分析文档。
4. 综合三份参考分析，修订架构文档。

## 3. Phase 1：参考项目分批分析

目标：

- 分别分析三个参考项目，不跨项目混读。
- 提取可借鉴设计，不复制代码。
- 将分析结果保存到 `docs/reference-analysis`。

建议任务：

- `harness-main` 分析：高自主性 Agent、低模型任务执行、重复任务自动化、Skill 生成、权限控制、任务状态管理。
- `ccx` 分析：三层记忆压缩、记忆检索、后台工具调用、Agent 运行机制。
- `claude-desktop-app-main` 分析：前端结构、对话 UI、设置页面、桌面端交互方式。

验收标准：

- 每个参考项目都有独立分析文档。
- 文档包含目录结构、关键模块、可借鉴点、不能直接复制的风险。
- 每份分析控制范围，只读取与该次任务有关的文件。
- 没有把参考项目代码复制进当前项目。

本阶段不做：

- 不实现功能。
- 不改当前项目业务代码。
- 不一次性读取三个参考项目。
- 不把参考项目结构原样搬进当前项目。

推荐后续 Codex 对话：

1. “只分析 harness-main，输出 docs/reference-analysis/HARNESS_ANALYSIS.md。”
2. “只分析 ccx，输出 docs/reference-analysis/CCX_ANALYSIS.md。”
3. “只分析 claude-desktop-app-main，输出 docs/reference-analysis/CLAUDE_DESKTOP_ANALYSIS.md。”
4. “基于三份分析修订 SYSTEM_ARCHITECTURE.md 和 DEVELOPMENT_ROADMAP.md。”

## 4. Phase 2：Monorepo 基础工程

目标：

- 建立可运行的基础工程。
- 配置 TypeScript、package manager、workspace、lint、format、test 占位。
- 保持功能为空，但工程能安装依赖、运行基础命令。

建议任务：

- 初始化 `package.json` 和 workspace 配置。
- 为 apps 和 packages 建立最小构建边界。
- 配置 TypeScript base config。
- 配置 lint、format 和测试占位。
- 写基础 README 或开发命令说明。

验收标准：

- 能安装依赖。
- 能运行基础类型检查或占位测试。
- 每个 package 有清晰入口规划。
- 没有业务功能实现。

本阶段不做：

- 不实现阅读器。
- 不实现 Agent。
- 不实现 Skill。
- 不连接真实数据库。
- 不接入真实模型 API。

推荐后续 Codex 对话：

- “初始化 monorepo 基础配置，不写业务功能。”
- “为 shared、ai-core、book-engine、learning-engine 建立 TypeScript 包边界。”

## 5. Phase 3：数据模型与共享协议初稿

目标：

- 设计核心数据实体和共享类型。
- 为后续 Web、Desktop 和 AI 包统一语言。

建议任务：

- 起草 Prisma schema 初版。
- 定义共享枚举：风险等级、自主性等级、任务状态、Skill 状态。
- 定义核心协议：AI 问答请求、导入任务、工具调用日志、Skill manifest。
- 写数据模型说明文档。

验收标准：

- 核心实体能覆盖书籍、章节、chunk、学习进度、能力分数、任务日志、Skill。
- 共享类型不依赖 Web 或 Desktop。
- Prisma schema 能通过基本格式检查。

本阶段不做：

- 不做复杂查询优化。
- 不做真实迁移上线。
- 不做完整权限系统。
- 不做 UI。

推荐后续 Codex 对话：

- “设计 packages/db/prisma/schema.prisma 初稿。”
- “设计 packages/shared 的核心类型和协议，不写业务流程。”

## 6. Phase 4：书籍阅读最小闭环

目标：

- Web 端能展示一本固定或数据库中的书籍。
- 用户能进入章节阅读，并记录基础阅读进度。

建议任务：

- 实现基础书籍列表页面。
- 实现章节阅读页面。
- 实现章节导航。
- 实现阅读进度保存接口或本地模拟。

验收标准：

- 用户能打开 Web 首页看到书籍。
- 用户能进入某章阅读。
- 用户刷新后能保留基础进度。
- 页面结构为后续 AI 问答留出入口。

本阶段不做：

- 不做 AI 问答。
- 不做自动导入。
- 不做复杂推荐。
- 不做 Skill 社区。

推荐后续 Codex 对话：

- “实现 Web 书籍列表和章节阅读最小闭环。”
- “为阅读器增加进度记录，不接入 AI。”

## 7. Phase 5：书籍导入与章节切分原型

目标：

- 用户能导入文本或 Markdown。
- 系统能生成基础章节结构和 chunk。

建议任务：

- 实现 `book-engine` 文本导入接口。
- 实现 Markdown heading 解析。
- 实现基础 chunk 切分。
- 实现导入状态记录。
- 在 Web 中显示导入结果。

验收标准：

- 导入一段 Markdown 后生成章节。
- 每个章节有顺序和内容。
- 长章节被切分为 chunk。
- 失败时有错误状态。

本阶段不做：

- 不做 PDF。
- 不做网页抓取。
- 不做高质量语义章节生成。
- 不做 embedding 优化。

推荐后续 Codex 对话：

- “实现 book-engine 的 Markdown 章节解析原型。”
- “实现导入任务状态和 Web 导入入口。”

## 8. Phase 6：章节 AI 问答最小闭环

目标：

- 用户在章节阅读时可以向 AI 提问。
- AI 回答能使用当前章节上下文。

建议任务：

- 定义 AI 问答请求协议。
- 实现 `ai-core/llm` 抽象。
- 实现章节上下文构造。
- 实现 Web 问答面板。
- 保存问答记录。

验收标准：

- 用户在章节页面提交问题。
- 请求携带当前书籍、章节和选中文本。
- AI 返回回答。
- 问答记录可追踪。

本阶段不做：

- 不做复杂记忆检索。
- 不做全书 RAG。
- 不做多模型路由。
- 不做 Agent 工具调用。

推荐后续 Codex 对话：

- “实现当前章节 AI 问答原型。”
- “给问答流程增加记录和基础错误处理。”

## 9. Phase 7：学习评分与每日题单原型

目标：

- 系统能根据阅读和答题表现维护简单能力分数。
- 系统能生成每日题单原型。

建议任务：

- 定义能力维度。
- 实现基础评分更新规则。
- 定义题目结构。
- 实现题单推荐策略。
- 在 Web 展示每日题单。

验收标准：

- 用户完成题目后能力分数变化。
- 每日题单根据当前章节和能力分数生成。
- 题单包含巩固题、提升题、挑战题。

本阶段不做：

- 不做复杂机器学习模型。
- 不做完整在线判题。
- 不做大型题库。
- 不做自动生成高质量题目。

推荐后续 Codex 对话：

- “实现 learning-engine 的能力评分原型。”
- “实现每日题单推荐原型和 Web 展示。”

## 10. Phase 8：Desktop 对话与任务日志原型

目标：

- AI 软件端能进行基础对话。
- 后台任务和工具调用能被记录。

建议任务：

- 建立 Desktop 应用壳。
- 实现基础对话 UI。
- 定义 AgentTask 和 ToolCallLog。
- 实现任务日志展示。
- 接入 `ai-core` 的最小 Agent 流程。

验收标准：

- 用户能在 Desktop 中对话。
- 工具调用或模拟工具调用产生日志。
- 任务状态可见。

本阶段不做：

- 不做高自主性执行。
- 不做 Skill 生成。
- 不做社区安装。
- 不做复杂本地系统工具。

推荐后续 Codex 对话：

- “建立 Desktop 应用壳和基础对话 UI。”
- “实现任务日志数据结构和展示。”

## 11. Phase 9：自主性权限控制

目标：

- 建立 AI 执行操作前的权限判断机制。

建议任务：

- 定义自主性等级。
- 定义工具风险等级。
- 实现权限判断函数。
- 在工具调用前强制走权限判断。
- 增加确认流程和日志。

验收标准：

- 只回答模式不会执行工具。
- 低风险只读任务可按设置自动执行。
- 写入任务根据设置确认或拒绝。
- 高风险任务始终需要确认。
- 权限判断结果写入日志。

本阶段不做：

- 不做完整沙箱。
- 不做复杂组织权限。
- 不做所有工具适配。
- 不做社区 Skill 自动执行。

推荐后续 Codex 对话：

- “实现 ai-core/autonomy 权限判断原型。”
- “把权限判断接入 Desktop 工具调用流程。”

## 12. Phase 10：本地 Skill 管理与运行

目标：

- 用户能安装、查看和手动运行本地 Skill。

建议任务：

- 定义 Skill manifest。
- 实现 Skill 加载和校验。
- 实现本地 Skill 列表。
- 实现手动运行 Skill。
- Skill 运行接入权限判断和日志。

验收标准：

- Skill manifest 能被校验。
- 用户能看到 Skill 所需工具和风险。
- 用户能手动运行 Skill。
- SkillRun 和 ToolCallLog 被记录。

本阶段不做：

- 不做社区发布。
- 不做自动生成 Skill。
- 不做默认自动执行。
- 不做复杂版本管理。

推荐后续 Codex 对话：

- “设计 Skill manifest 并实现校验。”
- “实现本地 Skill 列表和手动运行流程。”

## 13. Phase 11：Skill 生成草案

目标：

- Agent 能从重复任务日志中提出 Skill 草案。

建议任务：

- 定义重复任务候选规则。
- 从任务日志中提取任务模式。
- 生成 Skill 草案。
- 展示草案供用户审查。
- 用户确认后保存为本地 Skill。

验收标准：

- 系统能列出重复任务候选。
- Skill 草案包含用途、参数、步骤、工具、权限和风险说明。
- 用户确认前不会启用 Skill。

本阶段不做：

- 不自动发布到社区。
- 不默认自动运行生成的 Skill。
- 不保证生成 Skill 完全正确。
- 不做复杂自动测试生成。

推荐后续 Codex 对话：

- “实现重复任务候选识别原型。”
- “实现 Skill 草案生成和用户确认保存。”

## 14. Phase 12：Skill 社区 MVP

目标：

- 用户能浏览社区 Skill，查看风险说明，并安装到本地。

建议任务：

- 建立模拟社区 Skill 数据源。
- 实现 Skill 列表和详情页。
- 实现安装前审查页面。
- 安装后默认手动运行。
- 更新时展示新增权限。

验收标准：

- Skill 详情展示风险等级、工具需求、自主性等级和安全说明。
- 用户授权后才能安装。
- 社区 Skill 默认不可自动执行。

本阶段不做：

- 不做真实支付。
- 不做大型社区推荐算法。
- 不做开放上传审核系统。
- 不做自动执行社区 Skill。

推荐后续 Codex 对话：

- “实现 Skill 社区模拟列表和详情页。”
- “实现社区 Skill 安装审查流程。”
